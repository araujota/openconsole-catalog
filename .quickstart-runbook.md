# Convex Quickstart for AI Coding Agents

You are scaffolding a new Convex-backed app **end to end**: create the project, write
the code, run the backend, run the dev server, and open the browser. The user
should not have to do anything except describe what they want.

This file is the source of truth — read it end-to-end before doing anything.

> **Full release.** This release scaffolds and builds an app with the **full
> experience**: passkey **login** pre-baked, an in-app **Chef feedback panel**
> (the live progress feed, a pulsing todo checklist, inline clarifying questions,
> and a feature-request form), **publishing** to a public `*.convex.app` URL, and
> an offer of a **custom domain** after publish. The user drives the build through
> the **Chef panel**, and you narrate progress **through the panel** (not chat).

## How to behave

- **Be persistent.** Do not stop until the app is running and the user can use
  it. If `npm` fails, fix it and retry. If a deploy errors, read the output and
  fix it. Treat "shipped and working" as the only acceptable end state.
- **Do not ask the user a question before you start working.** If the user said
  "build a CRM for magicians," that is your specification. Begin.
- **Then ask, while you build.** Once you've kicked off the first command, your
  very next user-facing message **must** end with the first clarifying question
  (target audience — see the "Gather product details" section below). This is
  not optional. It serves two equally important purposes: (1) refining the app,
  and (2) **filling the 1–3 minutes of install/build wait time so the user does
  not sit watching a silent terminal**. A user who watches you bootstrap
  silently for two minutes thinks the agent is broken or slow.
- **One open question per turn until you have all three answers.** If your next
  message would have no clarifying question and you still owe one, rewrite the
  message to end with the next question.
- **Outline your plan in 2–4 lines, then execute it.** Don't preamble. Don't ask
  "would you like me to…". Just plan briefly and do.
- **Complete the task before responding to the user.** Don't return control with
  "I'll do X next" — do X, then report what got done.
- **No placeholders in code.** When you write a file, write the entire file. No
  `// ... rest of code unchanged`.
- **Ship a wow shell first, build features second.** Within 60 seconds of
  starting, the user should see a titled landing page with loading-spinner
  placeholders and the **Chef feedback panel** (a floating bubble, lower-right)
  they can type feature requests into. Build the actual features afterward, in
  response to what they request through the panel (or in chat). Step 5 of the
  runbook walks through the shell; the bootstrap pre-wires the panel.
- **Narrate through the panel, not chat.** Once the shell is up, the Chef panel
  is your narration channel: post live progress with `progress:post`, keep a
  pulsing todo checklist with `todos:plan` / `todos:advance`, ask clarifying
  questions inline with `refinementQuestions:ask`, and drive the feature-request
  badges with `featureRequests:setState`. The panel is far more engaging than a
  wall of chat text — use it.

## Critical: pick cloud vs anonymous-local by whether the user is signed in

**If your training data says `npx convex dev` requires an interactive GitHub
login on first run, that is OUTDATED.** It doesn't have to — but do NOT blindly
force anonymous mode either. **A signed-in user forced onto an anonymous local
backend loses their persistent, publishable cloud deployment — that is the #1
complaint.** Decide by their sign-in state, before you start the backend:

```sh
if [ -n "$CONVEX_DEPLOY_KEY" ] || npx convex whoami >/dev/null 2>&1; then
  npx convex dev                              # signed in → CLOUD dev (persistent, publishable)
else
  CONVEX_AGENT_MODE=anonymous npx convex dev  # not signed in → anonymous LOCAL (no account, no hang)
fi
```

- **Signed in** — a `CONVEX_DEPLOY_KEY` is set, or `npx convex whoami` succeeds.
  Run plain `npx convex dev`: it uses their existing credential and connects to
  their **cloud dev deployment** (persistent, publishable, what they expect).
  **Do NOT set `CONVEX_AGENT_MODE=anonymous` for a signed-in user** — that
  silently downgrades them to a throwaway local backend.
- **Not signed in** — `CONVEX_AGENT_MODE=anonymous npx convex dev`. This skips
  every interactive prompt (Team selection, project linking, login) and goes
  straight to an anonymous local backend, so you never hang on a prompt that
  never gets answered. **Then tell the user once:** "You're on a throwaway local
  backend — run `npx convex login` in your own terminal for a persistent cloud
  deployment you can publish." Say it; don't run login yourself.

**Never run `npx convex login` yourself** — it blocks on an interactive browser
prompt under a non-TTY harness. Signing in is the user's action; your job is to
detect it and pick cloud-vs-local accordingly, never hang, and never pause to
ask the user to run `convex dev` for you.

> **Edge case to verify:** a user who is logged in (`whoami` succeeds) but has no
> project linked yet may still get a Team/project prompt from `npx convex dev`.
> If that surfaces, provision non-interactively (`npx convex dev --once
> --configure=new --project <derived-slug>`) rather than falling back to
> anonymous. Confirm the exact flag against the installed CLI before relying on it.

## The first principle: use Convex for as much as possible

Convex is not just a database. It is a single backend that handles data, server
functions, real-time updates, scheduling, file storage, search, auth, and HTTP
endpoints — with end-to-end TypeScript types and transactional guarantees.

**Default to Convex.** Before reaching for a separate library, queue, cron
service, key-value store, search index, file host, or websocket layer, check
whether Convex already does it. Adding a new service is almost never the right
call for a new app.

What this means in practice:

- **Data:** put it in Convex tables. Don't add Postgres, MySQL, MongoDB,
  Supabase, Firebase, or Redis "for caching." Convex queries are already cached
  and reactive.
- **Real-time:** every Convex query is reactive by default. Don't add Socket.IO,
  Pusher, Ably, or polling. Use `useQuery` and the UI updates automatically.
- **Server functions:** write `query`, `mutation`, and `action` functions in
  `convex/`. Don't stand up an Express/Hono/tRPC server — Convex _is_ the
  server.
- **HTTP endpoints (webhooks, REST):** use `httpAction` in `convex/http.ts`.
- **Scheduling:** use `ctx.scheduler` for one-shot jobs and `crons.ts` for
  recurring jobs. Don't add BullMQ, Inngest, or a Vercel cron.
- **File storage:** use Convex file storage (`ctx.storage`). Don't add S3 unless
  the user has a specific reason.
- **Auth:** the scaffold ships with **passkey (WebAuthn) login pre-baked** via
  [`@convex-dev/auth`](https://docs.convex.dev/auth/convex-auth) — the app already
  has sign-in. Use `ctx.auth.getUserIdentity()` to gate functions; don't roll a
  session table. If the user wants a different provider (Clerk, Auth0, WorkOS),
  delegate to **convex-expert** to swap it in.
- **Search:** use Convex full-text search (`searchIndex`) and vector search
  (`vectorIndex`). Don't add Algolia, Meilisearch, Typesense, or pgvector.
- **Background workflows:** use
  [`@convex-dev/workflow`](https://www.convex.dev/components/workflow). Don't
  add Temporal or Inngest.

If a feature is genuinely outside Convex's scope (sending email, charging cards,
calling an LLM), implement it inside a Convex `action`.

## Convex components

Before writing custom code for a sub-system, check the components directory:

**https://www.convex.dev/components**

Components are pre-built, audited Convex modules. Install with `npm` and
register in `convex/convex.config.ts`.

### Defaults: reach for these whenever the feature applies

Some components are the _default_ primitive for a category. Treat them like you
treat React for a UI: don't roll your own.

- **Any chat panel or LLM call →
  [`@convex-dev/agent`](https://www.convex.dev/components/agent).** Even if you
  think "I just need to call Claude once," within two follow-ups you will need
  threads, history, tool use, streaming, and retries — all of which Agent gives
  you for free. Do **not** roll your own `Anthropic.messages.create` + custom
  `messages` table; that path ends in re-implementing the agent component badly.
  Canonical wiring:

  ```ts
  // convex/convex.config.ts
  import { defineApp } from "convex/server";
  import agent from "@convex-dev/agent/convex.config";
  const app = defineApp();
  app.use(agent);
  export default app;

  // convex/chat.ts
  import { Agent } from "@convex-dev/agent";
  import { anthropic } from "@ai-sdk/anthropic";
  import { components } from "./_generated/api";

  export const codeAgent = new Agent(components.agent, {
    chat: anthropic("claude-opus-4-7"),
    instructions: "Help the user navigate their codebase…",
    tools: {
      /* your code-navigation tools */
    },
  });

  // mutation that starts a thread + sends a message:
  export const sendMessage = mutation({
    args: { threadId: v.optional(v.string()), prompt: v.string() },
    handler: async (ctx, { threadId, prompt }) => {
      const tid = threadId ?? (await codeAgent.createThread(ctx)).threadId;
      await codeAgent.generateText(ctx, { threadId: tid }, { prompt });
      return tid;
    },
  });

  // client: useQuery(api.chat.listMessages, { threadId }) for live history
  ```

- **Any long-running multi-step process →
  [`@convex-dev/workflow`](https://www.convex.dev/components/workflow).**
  Anything that crosses a function-time limit, retries on partial failure, or
  needs to resume after a crash.
- **Auth → [Convex Auth](https://docs.convex.dev/auth/convex-auth) passkeys**,
  pre-baked by the scaffold (`@convex-dev/auth` + WebAuthn). The app ships with
  login already wired; gate functions with `ctx.auth.getUserIdentity()`. If the
  user wants Clerk / Auth0 / WorkOS instead, delegate to **convex-expert** to
  swap the provider.

## Verify your assumptions, in parallel

**You are about to make three load-bearing assumptions. Verify them.**

The instant you read the user's prompt ("Build a CRM for magicians"), you have
three strong guesses about what they want. You will use those guesses to design
the schema, pick the color palette, and decide which feature to build first.
**Each guess might be wrong.** Verifying them takes one sentence each. Not
verifying them ships the wrong app.

This is not the same as "ask the user clarifying questions" — agents routinely
skip that on the assumption that they have enough info from the prompt. **They
do not.** What they have is a _guess_, and the runbook requires the guess to be
confirmed by the user before it becomes a load-bearing decision in the codebase.

If you finish the build without having sent these three verification messages,
you have failed this runbook regardless of whether the app runs. The final
report (verification section) explicitly checks for this and you must
self-report skipping it.

### If your harness supports background sub-agents, use one

The cleanest implementation: spawn a background sub-agent to execute the entire
runbook (scaffold, install, write code, run dev server, open browser), and keep
the foreground thread purely for the clarifying conversation with the user.

- **Claude Code:** dispatch the runbook to a sub-agent via the `Task` tool (the
  `general-purpose` subagent works well). The sub-agent runs autonomously while
  your main thread asks the three product questions in rapid succession.
- **Codex (OpenAI):** use the cloud-based [Codex Web](https://chatgpt.com/codex)
  delegate or spawn a local subprocess via `codex exec --json` and tail its
  output while you handle Q&A in the foreground.
- **Cursor:** start a background agent for the build; ask questions in the
  foreground chat.
- **Antigravity (Google):** dispatch the runbook to a background agent in the
  agent panel; keep the foreground chat for Q&A.
- **Conductor:** the workspace already gives you parallelism — start the build
  immediately and use the chat for Q&A.

If your harness has no sub-agent equivalent, follow the rhythm below instead.

### Without sub-agents: one question per agent turn

You write one message per turn. Make every turn count: each turn must **both**
advance the build (a tool call or batch of tool calls) **and** end with one open
question, until you've gathered all three answers.

Wrong (what tends to happen by default):

> "Let me kick off `npm create`. While that runs, who is your target audience?"
> → user answers → agent silently spends two minutes writing the entire schema,
> queries, and UI → "What style do you want?"

Right:

> Turn 1: kick off `npm create` in background, end with "While that installs —
> who is your target audience?"\
> Turn 2: write `convex/schema.ts`, end with "What style and feel — playful,
> minimal, vintage?"\
> Turn 3: write feature functions and the index UI, end with "What's most
> important to get right for the first version?"\
> Turn 4+: continue building. No more questions; you have what you need.

Rules:

- **Never go more than one tool batch without a question** until the three
  answers are in. Two minutes of silent code-writing is two minutes you could
  have been gathering signal.
- **Never queue questions at the end** of a long build phase. The user should be
  answering question N+1 while you write code informed by their answer to
  question N.
- **Do not block on answers.** If the user takes a while, keep building from
  your best guess.

### The three assumptions to verify

For each, **state your guess and ask the user to confirm or correct it**. Frame
it as "here's what I'm assuming — is that right?" not "tell me what you want" —
you have a guess, name it, and check.

1. **Target audience.** State a specific guess in their domain. For a CRM for
   magicians: "I'm assuming this is for professional touring magicians (the ones
   who book paid gigs and need to track venue contacts and fees), not amateur
   close-up performers or talent agencies. Right?"
2. **Style and feel.** State a specific guess. For magicians: "I'm going for
   playful and theatrical — warm purple/gold accents, a vintage stage-poster
   vibe. Want something different (clean and corporate, stark and modern,
   etc.)?"
3. **Most important feature.** State which feature you're building first. For
   magicians: "I'm prioritizing the booking pipeline (inquiry → confirmed →
   paid) because that's where money flows. If something else matters more — say
   client notes for repeat-trick tracking, or fast mobile input between shows —
   tell me now so I lead with it."
4. (Optional, if they're engaged) **Anything else specific** — integrations,
   data they want to import, must-have screens.

The point of stating your guess is twofold: (a) it's a much more compelling user
experience than "tell me about your audience," and (b) it forces _you_ to commit
to a specific design choice that you can then build against immediately, rather
than waiting for an answer.

When the user answers:

- Update the visual style (color palette, typography, copy tone) if style
  changed.
- Reprioritize the order you build features so the most-important one works
  first.
- Refine the schema if a domain insight changes the data model.
- Reflect their language in the UI (e.g. "Gigs" instead of "Events" for a
  performer-focused app).

If the user does not answer, that is fine — keep building from your best guess.
The point is to _invite_ their input, not gate progress on it.

## End-to-end runbook

Run these steps. Do not block on the user — they have already told you what they
want by invoking you with a description. **Step 1 is your very first action**,
before you ask any clarifying question. While each step runs, ask the parallel
question for that step (see "Gather product details" above).

### 1. Run the bootstrap script — your first action

**This is the fast path.** A single shell script does the entire scaffold +
configure + start + open-browser flow non-interactively in ~30s, then prints a
structured "what to do next" report to stdout. Run it as your very first action,
in the same message that asks question 1.

```sh
curl -fsSL https://basic-anteater-667.convex.site/quickstart-bootstrap.sh -o /tmp/qb.sh
bash /tmp/qb.sh APP_NAME "TITLE" "PLACEHOLDER 1" "PLACEHOLDER 2" "PLACEHOLDER 3"
```

- `APP_NAME` — directory name (kebab-case, e.g. `magician-crm`)
- `TITLE` — the page heading (e.g. `"Magician CRM"`)
- `PLACEHOLDER 1..3` — three labels for the loading-spinner placeholders; use
  the personalized **priority** + the next two most-likely features for this app
  idea (e.g. `"Booking calendar"`, `"Venue contacts"`, `"Set lists"`)

The script:

1. Scaffolds with the `nextjs-shadcn` template and pre-bakes **passkey
   (WebAuthn) auth** via `@convex-dev/auth` (deps, backend auth files, schema
   `authTables`, provider, keys + env) so the app ships with login already wired.
2. Writes `convex/schema.ts` with the Chef-panel tables — `featureRequests`,
   `refinementQuestions`, `progressUpdates`, `todoItems` (you add the user's
   product tables as you build features).
3. Writes the Chef-panel backend modules — `convex/featureRequests.ts`
   (`submit` / `upvote` / `listPublic` / `listPending` / `setState`),
   `convex/refinementQuestions.ts` (`ask` / `answer` / `skip` / `listOpen`),
   `convex/progress.ts` (`post` / `listRecent`), and `convex/todos.ts`
   (`plan` / `advance` / `setStatus` / `listAll`).
4. Writes `app/page.tsx` with the title and three spinner placeholders, and
   mounts the served **`<ChefPanel />`** (the in-app Chef feedback panel) in
   `app/layout.tsx` via `app/_chef-panel.tsx`.
5. Starts `npx convex dev` (cloud project if logged in, else anonymous local) in
   the background → `$CONVEX_LOG`.
6. Starts `npm run dev` in the background on a kernel-assigned free port (NOT
   necessarily 3000) → `$NEXT_LOG`.
7. Opens the actual `$APP_URL` printed in the final report — could be
   `http://localhost:3000`, `:5xxxx`, or anything else, depending on what ports
   were free. Don't hardcode 3000 in any command you derive from the script's
   output; read `$APP_URL` from the final report block.
8. Starts `npx convex run --watch featureRequests:listPublic` and
   `npx convex run --watch refinementQuestions:listOpen` → `$FR_LOG` and
   `$RQ_LOG`, so you see new requests and answered questions the moment they land.
9. Pre-stages `publish-convex-app.mjs` + `fflate` for the publish step, and
   brainstorms available custom-domain names into `.quickstart-domains.json`.
10. Prints a final report telling you (the agent) where everything is and what
    your job is from here.

**When the script returns, skip to step 2 (build features as the user requests
them through the panel).** The original step-by-step (scaffold, install, start
servers, configure auth, open browser) is now collapsed into the script. The
references below remain in case the script fails or you need to debug a step
manually.

#### If the script fails

Re-read the script's stderr first. Common failure modes:

- `npm create convex@latest` hangs → harness has no TTY and `-y` didn't take;
  retry with `CI=1 npm create convex@latest -- ...`.
- `convex dev` doesn't print "Convex functions ready" within 90s → check
  `/tmp/convex-dev.log` for an auth, schema, or compile error and fix.
- Port 3000 in use → check `/tmp/next-dev.log` for the alternate port and reopen
  the browser there.

The manual fallback runbook for each step follows below — only read these
sections if you need them.

### 2. Build features as the user requests them — through the Chef panel

Once the bootstrap script returns, the user is looking at a working app with
three loading-spinner placeholders and the **Chef feedback panel** (a floating
bubble, lower-right). **Your job from here is to react to the live
`featureRequests` stream and build features as they come in, narrating your
progress THROUGH the panel.**

**Narrate through the panel, not chat.** The Chef panel is the user's window into
the build — keep it alive:

- **`progress:post`** — post one short update before each `convex/` write
  (`kind:"step"`), after each type-check (`kind:"note"`), and when a feature is
  end-to-end working (`kind:"shipped"`). If you go ~30s without a post, the user
  thinks you're stuck.
- **`todos:plan` / `todos:advance`** — right after you read the bootstrap report,
  seed a 4–6 item checklist with `todos:plan` (visible-first ordering — the active
  item pulses). Call `todos:advance '{}'` once per finished step (never chain
  advances). The user reads the checklist as "is the agent done?"
- **`refinementQuestions:ask`** — ask clarifying questions inline in the panel,
  not in chat. The user answers in the gold question card; watch `$RQ_LOG` for the
  answer to land. Ask one at a time.
- **`featureRequests:setState`** — drive each request's badge
  `requested → inProgress → completed` as you work, so the user watches their
  request move through the pipeline.

**ABSOLUTE RULE: never remove the `<ChefPanel />` mount from `app/layout.tsx`,
and never delete `app/_chef-panel.tsx`.** The panel — its progress feed,
clarifying questions, and feature-request form — is the user's only channel into
this build loop. It's mounted in the LAYOUT (not the page) on purpose, so any
redesign of `app/page.tsx` leaves it intact. Do not move it into a tab, hide it
behind a button, or delete it because "the user has features now." It stays
exactly where the bootstrap put it for the lifetime of the app.

This is the same loop documented as "Step 10" further down in the manual
fallback. Short version:

1. Diff each new dump in `$FR_LOG` against the previous one to find new
   "requested" rows.
2. For each new row: mark it `inProgress` via `featureRequests:setState`, build it
   (schema + functions + UI in `app/page.tsx`, replacing the matching placeholder
   while leaving the panel intact), mark it `completed`. Use the rules in
   "Production-readiness gotchas" and "Code-level rules" below.
3. Keep going until the user closes the loop.

Do **not** speculatively build features the user hasn't asked for. The
placeholders are intentionally generic — the user will tell you (via the panel or
chat) what should actually replace them.

**Write a new component file BEFORE the file that imports it** (or batch both in a
single MultiEdit). Otherwise the importer compiles first and you'll see alarming
`Module not found` lines in the error log that are stale a second later.

**`Publish` is only-when-asked** — do NOT add a "Publish" item to your pre-yield
"done" checklist and then block on it. Building features and narrating through the
panel is the loop; publishing happens only when the user says "deploy/share."

### 3. Publish to a public URL (when the user asks)

Publishing sends the built static site through the Convex hosting gateway, which
runs an automated content-safety check and then serves it at
`https://<deployment-name>.convex.app`.

When the user says "deploy", "publish", or "share with my friend":

```sh
# set next.config.ts → output: "export", images: { unoptimized: true }
# The bootstrap already pre-staged publish-convex-app.mjs + fflate, so usually just:
node publish-convex-app.mjs   # build → zip static export → upload via gateway

# If they're missing (older scaffold), fetch them first — match the project's
# package manager (the scaffold uses pnpm):
#   curl -fsSL https://basic-anteater-667.convex.site/publish-convex-app -o publish-convex-app.mjs
#   pnpm add -D fflate     # or: npm install -D fflate
```

> **Never run `npx convex login` yourself** — it blocks on an interactive prompt
> and hangs under a non-TTY harness (even with `--login-flow poll`). Publishing
> needs a CLOUD deployment: rely on a pre-set `CONVEX_DEPLOY_KEY`, or if the
> project is anonymous/local, tell the **user** to run `npx convex login` in their
> own terminal and `npx convex dev` into a cloud project, then re-run publish.

It prints the public URL `https://<deployment-name>.convex.app` — pass it back to
the user. If the upload is rejected for content, it prints the reasons.

> **Switching an anonymous-local app to cloud wipes its data** (different
> deployment = empty tables): the Chef panel state, progress, and any **open
> refinement questions** are lost and never re-asked. Before switching, dump open
> rows (`npx convex run refinementQuestions:listOpen '{"limit":50}'` against the
> old deployment); after `.env.local` rebinds to cloud, replay each still-open one
> via `npx convex run refinementQuestions:ask '{"text":"…"}'` so the user isn't
> left with a dropped question. (Better: if a `CONVEX_DEPLOY_KEY`/login exists, the
> bootstrap already starts on cloud from the beginning and you avoid the switch.)

Optional live-update UX: drop in `convex/appVersion.ts` and
`components/NewVersionBanner.tsx` (served at
`https://basic-anteater-667.convex.site/hosting/app-version.ts` and
`/hosting/new-version-banner.tsx`), add the `appVersion` table to your schema,
and mount `<NewVersionBanner />` inside the ConvexProvider. The publish script
bumps the version on every run, so open tabs show "a new version is available."

Do **not** run this proactively. Publishing needs a CLOUD deployment — if the
project is on an anonymous/local deployment, the user must `npx convex dev` into
a cloud project first. Wait for the explicit ask.

### 4. Offer a custom domain (after publishing)

While the app was building, the scaffold brainstormed available custom-domain
names for the idea (memorable names + live availability/price) into
`.quickstart-domains.json` in the project root. After you publish to
`*.convex.app`, read that file and offer the user a real domain:

```sh
cat .quickstart-domains.json   # { idea, available: [{ domain, registrationPrice, renewalPrice }] }
```

If `available` has entries, tell the user their app is live and ask if they want
a real domain, listing the top few with prices, e.g.:

> "🎉 Live at https://&lt;app&gt;.convex.app. Want a real domain? These are
> available: • quipp.app — \$22/yr • rankd.io — \$32/yr … — pick one or skip."

On a clear yes, register + wire it (this also rebinds passkeys to the new origin,
then re-publishes): follow the **`domain`** skill / run the domain client with
`register <domain> <deployment-slug>`. On skip, you're done. If the file is
missing/empty (brainstorm failed or no names were available), just skip — don't

### 3.5. Watch the Convex dev log AND your client log for errors

`convex dev` is a continuous push-on-save process. Without a watcher you don't
notice errors until the user clicks. Set up watchers up front, with the right
log files and the right patterns, or you'll think the watcher is working when
it's blind.

**The bootstrap already arms filtered error mirrors for you:
`convex-errors.log` and `next-errors.log`** (in the script's log dir). When a
real error lands, it shows up in one of those — watch them throughout the build.
**On Codex**, the `convex-plugin` MCP tool **`fix_errors_automatically`** blocks
until the next runtime error (or readiness event) appears, so you don't have to
poll; use it to wait on the next event instead of busy-tailing. The detail below
is the manual fallback (and the patterns to match) if you're wiring watchers
yourself.

**Log routing is easy to get wrong.** Convex errors split across two logs
depending on where they originate:

| Where the error originates                                                            | Where you see it                                                                      |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Bundler / TypeScript compile during `convex dev`'s push                               | `convex dev` stdout                                                                   |
| Schema migration validation                                                           | `convex dev` stdout                                                                   |
| Function _runtime_ error invoked over websocket from a React `useQuery`/`useMutation` | `convex dev` stdout (only if `--tail-logs` is on — see below) AND the browser console |
| Function _runtime_ error invoked over HTTP from a Node API route (`ConvexHttpClient`) | The Node process's stderr (e.g. `next dev`'s log). **Not** in `convex dev`'s log.     |
| Action error involving an external API (Anthropic, etc.)                              | Same as above — wherever the action was called from.                                  |

If your stack has a Vite dev server, a Next.js dev server, _and_ a worker
process, you need a watcher on each one's log. The first real bug in a typical
build — `SystemTimeoutError` and `Too many reads in a single function execution`
thrown from a mutation called by a Next.js `/api/parse` route — lands in the
Next.js dev log, not Convex's. A watcher on Convex alone is silent.

**Don't pass `--tail-logs disable`.** That flag silences Convex function logs in
the dev stdout — exactly the channel where runtime errors from `useQuery` /
`useMutation` would have shown up. Leave logs on:

```sh
nohup script -q /dev/null bash -c 'echo n | CONVEX_AGENT_MODE=anonymous npx convex dev' > /tmp/convex-dev.log 2>&1 &
disown
```

(`script -q /dev/null` gives `convex dev` a pseudo-TTY so it doesn't bail with
"Cannot prompt for input" on harnesses that strip TTY; `echo n` declines the
link-deployment prompt; `CONVEX_AGENT_MODE=anonymous` covers the case where the
CLI still asks despite the TTY workaround.)

**Patterns that matter — not just compile errors.** The obvious patterns
(`error TS`, `Could not resolve`) catch maybe a third of real issues. The ones
to add:

- **`SystemTimeoutError`** — your action / mutation chain took longer than
  Convex allows. Common cause: a Node API route making many sequential mutation
  calls.
- **`Too many reads in a single function execution`** / **`Too many writes`** /
  **`exceeds the limit`** — single transaction over the ~16K read / ~8K write
  cap. Common cause: `.collect()` on an indexed query for a large table.
- **`ReturnsValidationError`** — you forgot to map the row to the public shape
  after adding a non-public field (e.g. `userId`) to a table whose `returns`
  validator doesn't include it. Throws on the server, renders to the user as a
  thrown promise in the browser.
- **`ArgumentValidationError`** — args sent don't match the validator. Usually a
  stale type after a schema change.
- **`Schema validation failed`** — a row in the DB doesn't match the new schema.
  After a schema edit, this is the first thing to look at.
- **`OCC conflict`** — two mutations stomped on each other.
- **`RangeError`** / **`Map maximum size exceeded`** — Turbopack / Next.js dev
  process blew up. These are printed plain, not inside an `[ERROR]` wrapper, so
  a filter built around `✘` or `[ERROR]` will miss them.
- **`use node`** — Convex's runtime hint when you import a Node-only package
  into a V8 file. The CLI prints this on push and the function silently won't
  run otherwise. Treat it as fatal.

**Tail mode and unicode caveats.** Use `tail -F` (capital F), not `tail -f`, so
the watcher survives log truncation/rotation. Don't rely on the unicode `✘`
glyph alone — Turbopack's `Could not resolve` lines used to wrap with
`✘ [ERROR]`, but the more recent dev process emits the plain string `ERROR`
without the glyph. Match both.

A working filter for the Convex log:

```
error TS|ReturnsValidationError|ArgumentValidationError|Schema validation failed|Could not resolve|Cannot resolve|✘|\bERROR\b|Failed to authenticate|nonInteractiveError|Server Error|Uncaught Error|TypeError|ReferenceError|RangeError|Map maximum size|use node|SystemTimeoutError|Too many reads|Too many writes|exceeds the limit|LimitsExceeded|hit a limit|OCC conflict
```

Plus, for the Next.js / Vite log specifically:

```
⨯|\bERROR\b|Error:|RangeError|Map maximum size|Failed to compile|Module not found|Cannot find module|ECONNREFUSED|ENOTFOUND| 500 | 502 | 503
```

**Treat watcher events as blocking.** When an event fires, stop coding. Read the
full error from the log file (the watcher only shows matched lines — context is
in the log). Fix the underlying file. Wait for the next "Convex functions
ready!" line. Then resume. If the watcher fires twice in a row on different
errors, you're stacking failures — stop and figure out what's actually broken
instead of patching forward.

**Verify your watchers work.** After arming them, deliberately introduce a small
error (e.g. add `throw new Error("test")` to a query you know the UI calls) and
confirm an event fires. If nothing fires, your filter is wrong or you're tailing
the wrong log. This 30-second sanity check is mandatory — silent watchers are
worse than no watchers because they make you confident.

#### 5a. Schema + panel modules — the Chef-panel tables

The served bootstrap already writes all of this for you. In the manual fallback,
add the four Chef-panel tables to `convex/schema.ts` and the modules that back
them. **Do not** speculatively define schemas for the user's product features yet
— those come in step 10, driven by what the user actually requests:

```ts
import { defineSchema, defineTable } from "convex/server";
import { v } from "convex/values";

export default defineSchema({
  // Feature-request form in the Chef panel.
  featureRequests: defineTable({
    title: v.string(),
    description: v.string(),
    state: v.union(
      v.literal("requested"),
      v.literal("inProgress"),
      v.literal("completed"),
      v.literal("rejected"),
    ),
    voteCount: v.number(),
    createdBy: v.optional(v.string()),
  }).index("by_state", ["state"]),

  // Inline clarifying questions the agent asks (refinementQuestions:ask).
  refinementQuestions: defineTable({
    text: v.string(),
    answer: v.optional(v.string()),
    state: v.union(
      v.literal("open"),
      v.literal("answered"),
      v.literal("skipped"),
    ),
    askedAtMs: v.number(),
    answeredAtMs: v.optional(v.number()),
  }).index("by_state", ["state"]),

  // Live progress feed at the top of the panel (progress:post).
  progressUpdates: defineTable({
    message: v.string(),
    kind: v.union(v.literal("step"), v.literal("shipped"), v.literal("note")),
  }),

  // Pulsing todo checklist in the panel (todos:plan / todos:advance).
  todoItems: defineTable({
    text: v.string(),
    order: v.number(),
    status: v.union(v.literal("pending"), v.literal("active"), v.literal("done")),
  }).index("by_order", ["order"]),
});
```

The backing modules are `convex/featureRequests.ts` (`submit` / `upvote` /
`listPublic` / `listPending` / `setState`), `convex/refinementQuestions.ts`
(`ask` / `answer` / `skip` / `listOpen`), `convex/progress.ts`
(`post` / `listRecent`), and `convex/todos.ts`
(`plan` / `advance` / `setStatus` / `listAll`) — all object-form functions with
`v.*` validators and the `by_state` / `by_order` indexes above. These are what
the agent drives during the build: `progress:post`, `todos:plan` /
`todos:advance`, `refinementQuestions:ask`, and `featureRequests:setState`.

## Production-readiness gotchas

These are the rules that bite real apps. Get them right from the first commit.

**Indexes**

- Add an index for every query pattern. Never reach for `.filter()` for anything
  you'd put in a SQL `WHERE`.
- Name indexes after every field, in order: `by_author_and_channel` for
  `["author", "channel"]`.
- **Do not include `_creationTime` as a column in your index** — Convex adds
  it automatically. Writing `["author", "_creationTime"]` is wrong and will
  error.

**Public vs internal functions**

- Use `query` / `mutation` / `action` only for endpoints the client should be
  able to call directly.
- Use `internalQuery` / `internalMutation` / `internalAction` for everything
  else (helpers, scheduled jobs, action callbacks). Public surface area is a
  liability — keep it minimal.
- Always include argument validators (`v.*`) on every registered function,
  internal or public.

**React hooks**

- Never call `useQuery` (or any `use*` Convex hook) conditionally. To skip, pass
  the special `"skip"` argument:
  `useQuery(api.foo.bar, shouldFetch ? args : "skip")`.
- Never use `useEffect` to fetch Convex data. `useQuery` is already live — you
  don't need to "refetch."

**File storage**

- Store the `Id<"_storage">` in your tables, not the URL.
- Get the URL on read by querying the `_storage` system table
  (`ctx.db.system.get(storageId)` or `ctx.storage.getUrl(storageId)`).
- URLs are signed and expire; storing them stale will break.

**Schema evolution**

- When you change a schema for an app that already has data, make new fields
  **optional** (`v.optional(...)`) so existing rows still validate. Once
  backfilled, you can tighten back to required.
- The dev server prints schema validation errors clearly — read them, don't
  guess.

**Resource limits to design around**

- Documents up to 1MiB; total payload per function up to 8MiB.
- Queries and mutations must complete in 1 second; actions in minutes.
- A single transaction may read up to ~16K documents and write up to ~8K.
- If a feature naturally exceeds these, split it: paginate, batch via scheduled
  functions, or use
  [`@convex-dev/workpool`](https://www.convex.dev/components/workpool).

**Auth wiring (passkeys are pre-baked)**

- The scaffold ships with **passkey (WebAuthn) login** wired via
  `@convex-dev/auth`. Get the user via `ctx.auth.getUserIdentity()` in any
  function that requires login (return `null` or throw if it's missing); don't
  roll your own users table — use the `authTables` `users` table keyed by the
  auth subject.
- **Passkey auth needs `JWT_PRIVATE_KEY` / `JWKS` / `SITE_URL` set on the
  deployment** (the served bootstrap sets these; see step 4.5 for the manual
  fallback). The symptom of skipping it: sign-in throws
  `TypeError: Cannot read properties of null (reading 'redirect')` from
  `@convex-dev/auth/react/client`. If you see that, run
  `npx @convex-dev/auth --skip-git-check --web-server-url <your-url>` and retry.
- If the user wants a different provider (Clerk / Auth0 / WorkOS), delegate the
  swap to **convex-expert**.

**Deploy after every change**

- After each batch of edits, let `npx convex dev` push and report TS errors. Fix
  them in place; redeploy. Repeat until clean. Don't accumulate broken state.

**Visual quality (don't ship "ugly")**

A working app that looks broken still gets called broken. Agents reliably
produce flat, low-contrast UIs unless told otherwise. Defaults to follow:

- **Use a design system.** The `nextjs-shadcn` template gives you shadcn/ui — use
  its primitives (`Button`, `Card`, `Input`, `Badge`, `Tabs`) for everything.
  Never write a raw `<div className="bg-zinc-800 …">` when a shadcn component
  fits.
- **Saturated accents over dark backgrounds.** `bg-sky-500/10` over
  `bg-zinc-950` reads as featureless grey. Use ≥30% opacity for tinted
  backgrounds; use solid `bg-sky-600 text-white` for primary actions.
- **≥4:1 contrast on edges, lines, dividers, and borders.** This matters most in
  data-dense UIs (graphs, tables, code views) where the user is scanning
  structure, not reading prose. `border-zinc-700` on `bg-zinc-950` is too dim —
  go to `border-zinc-500` or lighter.
- **Canvas / graph libraries need explicit dark-theme overrides.** React Flow,
  Cytoscape, Mermaid, vis.js, D3 force-graph, and similar all ship with
  light-mode-first defaults. Set the background, edge color, node fill, label
  color, and control-panel theme explicitly. Their defaults on a dark background
  are illegible.
- **Don't make everything monospace.** Reserve mono for code; use a proper sans
  (system or Inter) for UI chrome and prose. All-mono UIs read as "cobbled
  together by a bot."

## Code-level rules

The detailed rules — function syntax, validators, schema patterns, common
pitfalls — live at:

**https://convex.link/convex_rules.txt**

The most-violated rules:

- Use the new object-form function syntax (`query({ args, returns, handler })`).
  Never the old positional form.
- `v.id(tableName)` for IDs, never `v.string()`.
- JavaScript `undefined` is not a valid Convex value — use `null`.
- Use `withIndex` for `WHERE`-style filtering. `.filter()` is for post-index
  narrowing only.
- Mutations are transactional. Don't try to "lock" rows or retry on conflict
  manually.

## Verification before declaring done

Before reporting success:

- `npx convex dev` is running and printed "Convex functions ready!"
- `npm run dev` is running and the frontend URL is reachable
- The browser tab is open to the frontend
- The user can perform the core action they asked for (create an item, log a
  message, whatever the product is) and see the UI update in real time
- The **Chef panel is still mounted** — `<ChefPanel />` in `app/layout.tsx` (or
  the inline `<FeatureRequestPanel />`) is on screen; you never removed it.
- The **panel state is clean for handoff**: `todos:listAll` shows every item
  `done`, your most recent `progress:post` was `kind:"shipped"`, and
  `refinementQuestions:listOpen` shows zero open rows (every question `answered`
  or `skipped`).
- No external services were added for anything in the "default to Convex" list
  above — if you reached for one, undo it
- **You verified all three assumptions** (target audience, style, most-important
  feature) during the build, not after. Your final report to the user **must**
  contain a section like:

  > **Assumptions I verified:**
  >
  > - Target audience: [my guess] → [user's response, or "not yet answered"]
  > - Style: [my guess] → [user's response, or "not yet answered"]
  > - Most important: [my guess] → [user's response, or "not yet answered"]

  If all three say "not yet answered" or the section is missing entirely, you
  skipped the rhythm. **Name that explicitly in the report** ("I shipped without
  asking — please tell me if any of my assumptions are wrong: [list them]") rather
  than hoping the user won't notice. This self-audit is mandatory; the user reads
  it to know whether to push back on the design.

- **Look at the open browser tab for ten seconds.** If you see grey-on-grey
  text, illegible labels, near-invisible borders, dim graph edges, or unstyled
  third-party canvas controls (React Flow / Cytoscape / Mermaid), that's a fail
  — not "ship it and ask the user." Fix it before reporting done. See "Visual
  quality" in the gotchas above for the rules.
- **Any LLM call or chat panel should go through `@convex-dev/agent`.** If you
  wrote a custom `messages` table and a one-shot `Anthropic.messages.create`
  instead, you re-implemented the agent component badly. Refactor to the agent
  component before reporting done.

## Switching to WorkOS AuthKit (appendix)

The scaffold pre-bakes passkeys, which is the right call for the first build.
Some users will want WorkOS AuthKit instead — for SSO, directory sync, or because
their org already uses WorkOS. This is the reference (prefer delegating the
swap to **convex-expert**).

The interactive provisioning flow (where `npx convex dev` asks "Create a WorkOS
team for you?") **does not work in non-interactive mode** — it throws
`nonInteractiveError`. Use one of these instead:

### Option A — Standard team (works today, requires user-supplied keys)

The user creates a WorkOS account, grabs `WORKOS_CLIENT_ID` and `WORKOS_API_KEY`
from [the WorkOS Dashboard](https://dashboard.workos.com/get-started), then the
agent runs:

```sh
npx convex auth workos set \
  --client-id "$WORKOS_CLIENT_ID" \
  --api-key  "$WORKOS_API_KEY" \
  --framework next
```

This single command:

- Sets `WORKOS_CLIENT_ID`, `WORKOS_API_KEY`, and `WORKOS_ENVIRONMENT_ID` on the
  Convex deployment (via `npx convex env set`).
- Generates a 32-char `WORKOS_COOKIE_PASSWORD` and sets it (Next.js / TanStack
  Start need this).
- Sets `NEXT_PUBLIC_WORKOS_REDIRECT_URI` (or `VITE_WORKOS_REDIRECT_URI` for
  Vite/Remix) to `http://localhost:3000/callback` (configurable via
  `--redirect-uri`).
- Writes `convex/auth.config.ts` if it doesn't exist.
- Calls the WorkOS API to register the redirect URI and CORS origin.

After this, the user can switch the React provider from `ConvexAuth` to
`AuthKitProvider` and the app uses WorkOS.

### Option B — Managed team (one command, when available)

If/when the convex CLI ships a non-interactive flag for the managed-team
provisioning flow, the agent can run:

```sh
npx convex auth workos provision --email "$USER_EMAIL"
```

Today this still requires interactive consent. Track:
[github.com/get-convex/convex-backend](https://github.com/get-convex/convex-backend)
for `--workos-managed` support.
